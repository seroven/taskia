# Base de datos de Taskia

Taskia usa **PostgreSQL**. Son **19 tablas** y viven todas en el schema `taskia`, no en `public`.

Este documento explica para qué sirve cada tabla y cómo se relacionan. Si buscas el *qué hace la app*, eso está en [PRODUCTO.md](PRODUCTO.md); acá está el *dónde se guarda*.

La fuente de verdad del esquema es [`taskia_backend/db/schema.pg.sql`](taskia_backend/db/schema.pg.sql). No hay ORM: el backend escribe SQL a mano.

---

## Convenciones que valen para todas las tablas

Antes de mirar tabla por tabla, conviene saber estas seis reglas, porque se repiten en todas.

**Identificadores.** Las tablas con `id` propio usan `BIGINT GENERATED BY DEFAULT AS IDENTITY`. Algunas no tienen `id`: cuando la fila es una extensión 1 a 1 de otra cosa, la clave primaria es directamente la del dueño (por ejemplo `study_sessions.task_id`).

**Instantes.** Todo momento en el tiempo es `TIMESTAMPTZ` y se guarda en UTC. Se escriben con `NOW()` de Postgres o con el default de la columna, nunca con una hora armada en el servidor de Node.

**Fechas de calendario.** `tasks.due_date` es `DATE`, no un instante. Es un día del calendario y no se convierte a ninguna zona. Ver [Fechas y zonas horarias](#fechas-y-zonas-horarias).

**Booleanos.** Son `BOOLEAN` de verdad (`TRUE`/`FALSE`), no `0`/`1`.

**Listas de valores.** No se usa el tipo `ENUM`. Los campos con opciones fijas son `TEXT` con un `CHECK`, así agregar un valor es un `ALTER` y no una migración de tipo. El resumen de todos está en [Valores permitidos](#valores-permitidos).

**`updated_at`.** Donde existe, lo mantiene el trigger `set_updated_at()`, que corre `BEFORE UPDATE`. No hay que actualizarlo a mano. Lo tienen nueve tablas: `users`, `tasks`, `study_sessions`, `study_boards`, `user_study_memory`, `study_worlds`, `study_missions`, `study_mission_sessions` y `study_mission_boards`.

## Mapa de relaciones

```
users ─┬─ courses ────────────────┬─ tasks ─┬─ study_sessions
       │                          │         ├─ study_messages
       │                          │         └─ study_boards
       ├─ user_study_memory       │
       │                          │
       ├─ study_worlds ─┬─ study_world_courses (courses)
       │                └─ study_missions ─┬─ study_mission_sessions
       │                                   ├─ study_mission_messages
       │                                   └─ study_mission_boards
       │
       ├─ study_challenges ─── study_challenge_questions ─── study_challenge_answers
       └─ llm_usage

difficulties ─── tasks            (catálogo, no cuelga de users)
study_challenge_presets           (catálogo suelto, sin claves foráneas)
```

Los dos caminos del producto se ven en el mapa: `tasks` por un lado, `study_worlds` por el otro, y `courses` como la pieza que une ambos.

## 1. Cuentas y catálogos

### `users`

Las dos caras de la app viven en la misma tabla; las distingue `role`.

| Columna | Tipo | Nota |
| --- | --- | --- |
| `id` | bigint | PK |
| `username` | varchar(50) | único |
| `email` | varchar(255) | único |
| `password_hash` | varchar(255) | hash bcrypt |
| `role` | text | `user` o `admin` |
| `is_active` | boolean | `false` = cuenta pausada |
| `created_at` / `updated_at` | timestamptz | |

`role` va entre comillas dobles en el SQL (`"role"`) porque es palabra reservada en Postgres. Pausar una cuenta es poner `is_active = FALSE`: el alumno no puede entrar, pero no se borra nada.

### `courses`

Las materias que el adulto asigna. Son del alumno, no del mundo.

| Columna | Tipo | Nota |
| --- | --- | --- |
| `id` | bigint | PK |
| `user_id` | bigint | → `users`, borrado en cascada |
| `name` | varchar(120) | único por alumno |
| `is_active` | boolean | `false` = archivada |
| `created_at` | timestamptz | |

La restricción `uq_courses_user_name` impide dos materias con el mismo nombre para el mismo alumno, pero dos alumnos sí pueden tener "Matemática". `uq_courses_id_user` repite `(id, user_id)` como único: no agrega una regla nueva sobre la materia, existe para que otras tablas puedan exigir que el `user_id` que guardan sea el de esa materia.

Archivar en lugar de borrar es a propósito: la materia deja de ofrecerse para cosas nuevas y el historial queda intacto. De hecho borrarla suele ser imposible, porque `tasks` y `study_world_courses` la referencian con `ON DELETE RESTRICT`.

No tiene `updated_at`.

### `difficulties`

Catálogo de tres filas que se siembra con el esquema: `low` → Bajo, `medium` → Medio, `high` → Alto, en ese orden (`sort_order` 1, 2, 3).

| Columna | Tipo | Nota |
| --- | --- | --- |
| `id` | bigint | PK |
| `code` | varchar(20) | único; lo usa el código |
| `name` | varchar(50) | único; lo ve el usuario |
| `sort_order` | int | orden de presentación |
| `created_at` | timestamptz | |

El código de la app decide por `code`, no por `id` ni por `name`. El candado para terminar una tarea mira `code = 'high'`.

## 2. El tablero de tareas

### `tasks`

Una fila por tarjeta del tablero. Es la tabla con más columnas y la que más índices tiene.

| Columna | Tipo | Nota |
| --- | --- | --- |
| `id` | bigint | PK |
| `user_id` | bigint | → `users`, cascada; además, junto con `course_id`, debe ser el dueño de esa materia |
| `course_id` | bigint | → `courses`, restringido |
| `difficulty_id` | bigint | → `difficulties`, restringido |
| `title` | varchar(255) | |
| `description` | text | opcional |
| `task_kind` | text | `daily` o `project` |
| `status` | text | `pending`, `in_progress`, `studying`, `done` |
| `board_order` | int | orden dentro de la columna |
| `study_passed` | boolean | el visto del tutor |
| `uses_board` | boolean | la sesión usa pizarra |
| `study_mode_chosen` | boolean | ya eligió chat o pizarra |
| `due_date` | date | día de entrega |
| `created_at` / `updated_at` | timestamptz | |

`status` son las cuatro columnas del tablero y `board_order` es la posición dentro de una de ellas; juntas con `user_id` forman el índice `idx_tasks_user_status_order`, que es el que sostiene el arrastrar y soltar.

`study_passed` es el candado del que habla el producto: lo pone el tutor cuando hay evidencia, y sin él una tarea de dificultad alta (o que pasó por `studying`) no se puede marcar `done`.

`due_date` es obligatoria. En una tarea `daily` se resuelve sola: es el día de hoy **según el calendario de quien la crea**, no del servidor. En una `project` la elige el alumno.

Hay índices sueltos por `user_id`, `course_id`, `difficulty_id`, `status`, `task_kind`, `due_date` y `created_at`, que son los filtros del tablero y del panel del adulto.

La clave `fk_tasks_course_owner` ata `(course_id, user_id)` a `courses (id, user_id)`. Una tarea no puede quedar con la materia de otro alumno.

## 3. El tutor del tablero

Cuatro tablas que guardan la conversación de una tarea. Las tres primeras cuelgan de `tasks` y se borran con ella.

### `study_sessions`

El estado de la sesión: una fila por tarea, no una por conversación. La PK **es** `task_id`, así que la relación es 1 a 1.

| Columna | Tipo | Nota |
| --- | --- | --- |
| `task_id` | bigint | PK y → `tasks`, cascada |
| `tutor_phase` | text | `understanding`, `practicing`, `reviewing` |
| `topic_summary` | text | de qué se trata la tarea |
| `context_summary` | text | resumen vivo de la charla |
| `hints_level` | int | pistas dadas |
| `created_at` / `updated_at` | timestamptz | |

`context_summary` es lo que hace que el tutor no repita preguntas: en cada turno se le manda este resumen, no el chat crudo. `tutor_phase` son las tres fases que el alumno ve en pantalla.

### `study_messages`

El chat, un mensaje por fila.

| Columna | Tipo | Nota |
| --- | --- | --- |
| `id` | bigint | PK |
| `task_id` | bigint | → `tasks`, cascada |
| `role` | text | `user` o `assistant` |
| `content` | text | |
| `from_voice` | boolean | se dictó por voz |
| `created_at` | timestamptz | |

Se lee siempre ordenado por `(task_id, created_at)`, que es justo el índice que existe. `from_voice` es lo que permite contar transcripciones aparte en el panel.

### `study_boards`

La pizarra de la tarea: una fila por tarea, con el dibujo entero serializado.

| Columna | Tipo | Nota |
| --- | --- | --- |
| `task_id` | bigint | PK y → `tasks`, cascada |
| `board_json` | text | grilla serializada |
| `updated_at` | timestamptz | |

`board_json` es `TEXT`, no `JSONB`: la app lo guarda y lo devuelve tal cual, nunca consulta dentro.

### `user_study_memory`

Memoria breve del alumno, transversal a todas sus tareas y temas. Una fila por alumno (la PK es `user_id`), con `memory_summary` y `updated_at`.

Es lo que le da continuidad al tutor entre sesiones distintas. No cuelga de ninguna tarea.

## 4. Mundos

### `study_worlds`

El contenedor ("Este trimestre", "Ciencias"). Tiene `id`, `user_id` (→ `users`, cascada), `title`, `description` opcional, `is_active` y `created_at` / `updated_at`.

`is_active = FALSE` es la baja del mundo: deja de listarse, pero la fila sigue. `uq_study_worlds_id_user` hace único el par `(id, user_id)` para que desafíos y vínculos puedan comprobar que el alumno es el dueño del mundo. El índice parcial `idx_study_worlds_user_active` cubre el listado de mundos vigentes.

### `study_world_courses`

Qué materias entraron a un mundo. Es una tabla puente y **no tiene `id`**: su clave primaria es el par `(world_id, course_id)`, lo que impide agregar dos veces la misma materia al mismo mundo.

| Columna | Tipo | Nota |
| --- | --- | --- |
| `world_id` | bigint | PK compuesta, → `study_worlds`, cascada |
| `course_id` | bigint | PK compuesta, → `courses`, restringido |
| `user_id` | bigint | el mismo alumno del mundo y de la materia |
| `sort_order` | int | orden dentro del mundo |
| `is_active` | boolean | `false` = materia desvinculada de este mundo |
| `created_at` | timestamptz | |

`user_id` no es decorativo. `(world_id, user_id)` apunta a `study_worlds (id, user_id)` y `(course_id, user_id)` apunta a `courses (id, user_id)`, así un mundo no puede enlazar la materia de otro alumno.

Quitar la materia del mundo no borra la fila: pone `is_active = FALSE` y desactiva las misiones de ese par. Volver a agregarla reactiva solo el vínculo; las misiones viejas siguen inactivas. El índice parcial `idx_study_world_courses_world_active` es el de las materias vigentes.

Borrar el mundo de verdad (eso solo ocurre si se borra el alumno, en cascada) borra estas filas. Borrar la materia del catálogo no, porque está restringido.

### `study_missions`

Cada misión es un tema de estudio dentro de una materia de un mundo.

| Columna | Tipo | Nota |
| --- | --- | --- |
| `id` | bigint | PK |
| `world_id` | bigint | → `study_worlds`, cascada |
| `course_id` | bigint | → `courses`, restringido |
| `title` | varchar(255) | |
| `description` | text | opcional |
| `status` | text | `pending`, `studying`, `mastered` |
| `uses_board` | boolean | el tema se practica en pizarra |
| `is_active` | boolean | `false` = el tema ya no se ofrece |
| `source_mission_id` | bigint | → `study_missions`, se pone en `NULL` |
| `sort_order` | int | |
| `created_at` / `updated_at` | timestamptz | |

`status` es el Por empezar → En marcha → Dominado del producto, y el progreso de la materia dentro del mundo se calcula contando cuántas misiones activas llegaron a `mastered`.

`(world_id, course_id)` apunta a `study_world_courses`. No puede existir una misión de una materia que nunca se vinculó a ese mundo. El par `(id, world_id)` es único para que un desafío pueda exigir que la misión sea de su mismo mundo.

`source_mission_id` apunta a otra fila de la misma tabla y registra de dónde se copió un tema al traerlo de otro mundo. Su clave foránea es `DEFERRABLE INITIALLY DEFERRED`: la validación se posterga al final de la transacción, lo que permite insertar un lote de misiones que se referencian entre sí sin pelear con el orden. Si se borra la misión original, este campo queda en `NULL` y la copia sobrevive.

El índice parcial `idx_study_missions_world_course_active` cubre las misiones vigentes de una materia.

Un trigger diferido, `assert_active_mission_link()`, corre al cerrar la transacción. Rechaza el commit si queda una misión activa cuyo mundo, o cuyo vínculo mundo-materia, está inactivo. La app desactiva en cascada; la base solo vigila.

## 5. El tutor de mundos

Mismo patrón que el tutor del tablero, pero colgando de `study_missions`. Son tablas separadas, no compartidas: una sesión de tarea y una de misión no se mezclan nunca.

### `study_mission_sessions`

| Columna | Tipo | Nota |
| --- | --- | --- |
| `mission_id` | bigint | PK y → `study_missions`, cascada |
| `tutor_phase` | text | `understanding`, `practicing`, `reviewing` |
| `topic_summary` | text | |
| `context_summary` | text | resumen vivo de la charla |
| `notebook_context` | text | el relato del cuaderno, fijo |
| `hints_level` | int | |
| `updated_at` | timestamptz | |

La diferencia con `study_sessions` son dos columnas: acá está `notebook_context` y no está `created_at`. `notebook_context` guarda el primer relato del alumno sobre su cuaderno y **no se vuelve a tocar**: el tutor lo recibe completo en cada turno para no preguntar cosas que no estén ahí, mientras `context_summary` sí se va actualizando.

### `study_mission_messages`

Igual que `study_messages` pero con `mission_id`: `id`, `mission_id`, `role`, `content`, `from_voice`, `created_at`. Su índice es `(mission_id, id)` en lugar de `(mission_id, created_at)`, así el orden de lectura es estable incluso entre mensajes del mismo segundo.

### `study_mission_boards`

Igual que `study_boards` pero por misión: `mission_id` como PK, `board_json` y `updated_at`.

## 6. Desafíos

Cuatro tablas en cadena: el intento, sus preguntas, las respuestas, y un catálogo de tamaños.

### `study_challenges`

Un intento de desafío.

| Columna | Tipo | Nota |
| --- | --- | --- |
| `id` | bigint | PK |
| `user_id` | bigint | → `users`, cascada; el mismo dueño del mundo |
| `world_id` | bigint | → `study_worlds`, cascada |
| `scope` | text | `mission`, `course` o `world`, con reglas abajo |
| `mission_id` | bigint | obligatorio si el alcance es un tema; se pone en `NULL` si el tema se borra de verdad |
| `course_id` | bigint | obligatorio si el alcance es una materia; en un tema puede venir y en un mundo no |
| `difficulty` | text | `warm`, `quest`, `boss` |
| `question_count` | int | preguntas que se pidieron |
| `status` | text | `in_progress`, `completed`, `abandoned` |
| `score` | smallint | `NULL`, o entre 0 y 100 |
| `started_at` | timestamptz | por defecto `NOW()` |
| `completed_at` | timestamptz | `NULL` hasta que se entrega |

`ck_study_challenges_scope` obliga el alcance:

- `mission`: `mission_id` presente. `course_id` puede venir, que es lo que manda la pantalla de la materia.
- `course`: `course_id` presente y `mission_id` vacío.
- `world`: los dos vacíos.

Además, `(world_id, user_id)` debe ser el dueño del mundo. Si `mission_id` viene, la misión tiene que ser de ese mundo. Si `course_id` viene, esa materia tiene que estar vinculada al mundo (aunque el vínculo ya esté inactivo: el intento viejo se conserva). Esas dos claves son `DEFERRABLE`, así que se revisan al cerrar la transacción. Cuando `mission_id` o `course_id` es `NULL`, Postgres no evalúa esa clave (`MATCH SIMPLE`).

Las dos fechas cuentan distinto: `started_at` siempre existe, y `completed_at` solo se llena al corregir, así que sirve para separar intentos entregados de abandonados. `score` admite `NULL` justamente por eso, y su `CHECK` lo mantiene entre 0 y 100.

Esta tabla **no** tiene `updated_at` ni trigger.

### `study_challenge_questions`

Las preguntas que generó la IA para ese intento.

| Columna | Tipo | Nota |
| --- | --- | --- |
| `id` | bigint | PK |
| `challenge_id` | bigint | → `study_challenges`, cascada |
| `mission_id` | bigint | de qué tema salió; se pone en `NULL` |
| `sort_order` | int | orden de presentación |
| `kind` | text | `multiple_choice`, `short_text`, `fill_blank`, `board_prompt` |
| `prompt` | text | el enunciado |
| `options_json` | jsonb | opciones, solo en opción múltiple |
| `answer_key` | text | la respuesta esperada |
| `requires_board` | boolean | hay que dibujar para responder |
| `prompt_draw_ops` | jsonb | dibujo del enunciado |
| `created_at` | timestamptz | |

Acá sí se usa `JSONB` y no `TEXT`, en `options_json` y `prompt_draw_ops`. Se leen ordenadas por `(challenge_id, sort_order)`, que es el índice que existe.

Guardar `mission_id` en cada pregunta es lo que permite que un desafío de materia o de mundo mezcle temas y después se sepa de dónde vino cada una.

### `study_challenge_answers`

Lo que respondió el alumno.

| Columna | Tipo | Nota |
| --- | --- | --- |
| `id` | bigint | PK |
| `question_id` | bigint | → preguntas, cascada; **único** |
| `user_answer` | text | opcional |
| `board_json` | text | lo que dibujó |
| `is_correct` | boolean | `NULL` mientras no se corrige |
| `answered_at` | timestamptz | |

La restricción `uq_study_challenge_answers_question` sobre `question_id` garantiza **una sola respuesta por pregunta**. Por eso, al entregar un intento, el backend borra las respuestas previas antes de insertar las definitivas: así un reintento no choca con la restricción.

`is_correct` en `NULL` significa "todavía no corregida", distinto de `FALSE`, que es "está mal".

### `study_challenge_presets`

Catálogo de cuántas preguntas lleva cada combinación. No tiene claves foráneas y su PK es el par `(scope, difficulty)`, así que hay exactamente nueve filas, que se siembran con el esquema:

| scope | warm | quest | boss |
| --- | --- | --- | --- |
| `mission` | 5 | 8 | 10 |
| `course` | 10 | 15 | 20 |
| `world` | 20 | 40 | 80 |

La cuarta columna es `label`, el nombre visible: Calentamiento, Aventura y Jefe final. Estos números son el techo: si hay poco material estudiado, la app genera menos para no inventar de la nada.

## 7. Consumo de IA

### `llm_usage`

Una fila por llamada al modelo. Es lo que alimenta las gráficas de uso y el costo estimado del panel.

| Columna | Tipo | Nota |
| --- | --- | --- |
| `id` | bigint | PK |
| `user_id` | bigint | → `users`, cascada |
| `kind` | text | qué disparó la llamada |
| `model` | varchar(80) | modelo usado |
| `prompt_tokens` | int | entrada |
| `output_tokens` | int | salida |
| `total_tokens` | int | |
| `created_at` | timestamptz | |

`kind` acepta cinco valores: `task_tutor`, `mission_tutor`, `transcribe`, `challenge_generate` y `challenge_grade`. Guardar el `model` en cada fila importa porque el precio por token depende de él y cambia con el tiempo.

Tiene dos índices pensados para el panel: `(user_id, created_at)` y `(kind, created_at)`.

El registro es deliberadamente tolerante a fallos: si insertar acá falla, la sesión del alumno sigue igual. Medir no puede romper lo que se está midiendo.

## Fechas y zonas horarias

Es la parte más fácil de romper, así que vale la regla explícita: **la base guarda en UTC, la web convierte**.

Hay dos clases de columnas y no se tratan igual:

| Clase | Tipo | Ejemplo | Cómo viaja al navegador |
| --- | --- | --- | --- |
| Instante | `timestamptz` | `created_at` | ISO 8601 UTC: `2026-09-11T02:26:59.000Z` |
| Día de calendario | `date` | `due_date` | `YYYY-MM-DD`, sin zona |

Un **instante** es un momento exacto. Se escribe con `NOW()` o con el default de la columna, el API lo serializa con `toInstantISO()` (que agrega la `Z`) y el navegador lo formatea en la zona de quien mira con `Intl`. El mismo dato se ve `02:26` en Lima y `09:26` en Madrid. Lo que nunca hay que hacer es mandar `"2026-09-11 02:26:59"` sin zona: el navegador lo lee como hora local y el desfase aparece en producción, donde el servidor corre en UTC.

Un **día de calendario** no tiene hora ni zona, así que convertirlo solo puede correrlo de fecha. Si una tarea vence el 10, vence el 10 en todo el mundo.

Cuando el panel agrupa actividad por día (las gráficas), el día civil se calcula con la zona **del visor**, que el frontend manda en el header `X-Timezone`. Eso vive en `taskia_backend/src/db/civilDate.ts`. Sin eso, una sesión de las 21:00 en Lima caería en el día siguiente, porque en UTC ya lo es.

## Qué se borra con qué

Hay dos capas. La app, cuando el alumno “borra” un mundo, una materia dentro del mundo o una misión, **no destruye la fila**: pone `is_active = FALSE`. Las sesiones, los mensajes, las pizarras y los desafíos siguen colgando de esa fila. Lo inactivo deja de salir en las listas; abrirlo por URL responde como si no existiera.

La cascada lógica, en una sola transacción:

- Desactivar un mundo desactiva sus vínculos de materia y sus misiones.
- Desactivar el vínculo de una materia desactiva las misiones de ese par mundo+materia.
- Desactivar una misión no toca al resto.

Volver a agregar la materia reactiva solo el vínculo. Los temas que se habían quitado no reaparecen.

Las claves foráneas, en cambio, actúan cuando sí hay un `DELETE` físico (borrar la cuenta del alumno, descartar un desafío a medias, o la cascada de esos borrados).

**`ON DELETE CASCADE` — se va con el dueño.** Borrar un `user` se lleva sus materias, tareas, mundos, desafíos y uso de IA. Borrar una `task` se lleva su sesión, sus mensajes y su pizarra. Borrar una `study_mission` se lleva su sesión, mensajes y pizarra. Borrar un `study_challenge` se lleva sus preguntas, y cada pregunta sus respuestas. Borrar un vínculo mundo-materia se lleva las misiones de ese par; la app ya no hace ese `DELETE`, pero la cascada sigue ahí por si se borra el mundo junto con el alumno.

**`ON DELETE RESTRICT` — protege el historial.** Una `course` no se puede borrar si tiene tareas o está en un mundo, y una `difficulty` no se puede borrar si hay tareas que la usan. Para eso está archivar (`is_active = FALSE`) en lugar de borrar. La misma idea de “mismo dueño” está en `fk_tasks_course_owner`, en el `user_id` de `study_world_courses` y en `fk_study_challenges_world_owner`.

**`ON DELETE SET NULL` — el hijo sobrevive.** `study_missions.source_mission_id`, y los `mission_id` / `course_id` de `study_challenges` y `study_challenge_questions`. Un desafío viejo no desaparece porque se haya borrado de verdad el tema del que salió: queda el intento, el puntaje y las respuestas, sin el vínculo. La baja lógica no dispara este caso, porque la fila sigue existiendo.

## Cómo se crea y actualiza el esquema

Desde `taskia_backend`:

```bash
npm run db:setup      # crea el schema y aplica schema.pg.sql
npm run db:migrate    # aplica schema.pg.sql si todavía no hay tablas
```

Hay variantes por entorno (`db:setup:qa`, `db:migrate:pd`), que solo cambian el `--env-file`. El script es `db/migrate.mjs` y el esquema `db/schema.pg.sql`.

El archivo es **idempotente** sobre una base vacía o ya creada con este mismo esquema: usa `CREATE TABLE IF NOT EXISTS`, `CREATE INDEX IF NOT EXISTS`, `CREATE OR REPLACE FUNCTION` y `ON CONFLICT DO UPDATE` en las siembras. Lo que **no** hace es alterar tablas que ya están creadas. Las columnas `is_active` de mundos y misiones, el `user_id` del vínculo y las claves compuestas solo aparecen si el schema se arma de cero.

Para aplicar esta versión hay que vaciar antes, por ejemplo `DROP SCHEMA taskia CASCADE;`, y después correr el setup. Volver a aplicar el archivo sobre las tablas viejas no migra nada y deja la base sin estas reglas.

El schema se elige con `PG_SCHEMA` (por defecto `taskia`) y la conexión con `PG_DSN`, o bien `PG_HOST` / `PG_PORT` / `PG_USER` / `PG_PASSWORD` / `PG_DATABASE`. En hosting va además `PG_SSLMODE=require`.

Las migraciones viejas de MySQL que quedan en `db/migrations/` **no** se aplican en Postgres. Son historia; el esquema vivo es `schema.pg.sql`.

## Trampas conocidas

Cosas que ya nos mordieron y conviene tener presentes al escribir SQL nuevo.

**El traductor de dialecto.** El backend escribe SQL con `?` y algo de sabor MySQL, y `src/db/sql.ts` lo reescribe a Postgres (`$1`, `ON CONFLICT`, `RETURNING`, booleanos). Traduce los booleanos **por nombre de columna**, y la lista es `is_active`, `from_voice`, `study_passed` y `uses_board`. Si escribes una condición sobre `requires_board`, `is_correct` o `study_mode_chosen`, usa `TRUE` / `FALSE` directamente, porque esas no están en la lista y `= 1` fallaría.

**Sintaxis que no cruza.** El borrado multi-tabla de MySQL (`DELETE a FROM tabla a JOIN ...`) no existe en Postgres y da un `syntax error` poco claro. Se escribe con un subquery o con `USING`.

**`role` es palabra reservada.** Siempre entre comillas dobles: `"role"`.

**Las tablas 1 a 1 no tienen `id`.** `study_sessions`, `study_boards`, `study_mission_sessions`, `study_mission_boards` y `user_study_memory` se buscan por la clave de su dueño. No hay un `session_id` que usar.
